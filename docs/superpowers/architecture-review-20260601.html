The Friction

The offline sync module is shallow. Rather than acting as a simple, abstract transaction ledger, it hardcodes exact database structures. It duplicates complete network mutation REST calls using raw fetch requests inside the Service Worker (sw.js) and Supabase JS query builders inside offlineSync.ts, scattering domain database rules across thread seams.

The Proposal

Deepen the module by making the Service Worker a dumb queue receiver that persists raw action payloads to IndexedDB and triggers a wakeup signal. Collapse all database mutation and playback logic strictly into offlineSync.ts, utilizing the official, type-safe Supabase JS SDK on the client side when the browser transitions online.

Architectural Wins

  • ✔ Locality: Playback mutations concentrate in one module.
  • ✔ Interface shrinks: Worker delegates all mutations to main.
  • ✔ Deletes 150+ lines of duplicate REST fetch code in sw.js.
  • ✔ Leverage: Re-uses deep type-safe Supabase JS clients.

The Friction

The notification state management is shallow. The client-only state store (useAppStore) performs backend database mutations directly in its actions (violating ADR-016), while subscription registration and query lifecycles are hardcoded inside a useEffect block in AuthProvider.tsx. Callers must interact with multiple separate files.

The Proposal

Collapse all notifications state, Postgres realtime listeners, and database mutations into a single, deep useNotifications custom hook utilizing TanStack Query mutations. Keep Zustand's store purely volatile and focused on client-side state.

Architectural Wins

  • ✔ Locality: Notification database logic concentrates in one hook.
  • ✔ Leverage: Callers get complete state, mutations, and updates in one call.
  • ✔ Adheres to ADR-016: Server state resides fully inside TanStack Query.
  • ✔ Interface shrinks: AppStore acts strictly as UI/Session store.

3. Abstract Real-time Database Subscription Channels

Worth exploring ports & adapters

Involved Files

📄 src/components/AuthProvider.tsx

The Friction

AuthProvider.tsx has a 100+ line setup subscribing to six distinct Postgres tables and broadcast channel feeds (announcements, assignments, polls, votes, submissions, acknowledgments). This is shallow because it couples the top-level Auth wrapper component to database schemas. If a new real-time table is added or query key is changed, it requires modifying AuthProvider.tsx inline.

The Proposal

Introduce a dedicated, deep RealtimeBroker with a clean pub/sub interface. The broker handles connection pooling, channel registration, and message dispatching, letting domain hooks subscribe to updates dynamically rather than hardcoding all table triggers inside a monolithic auth-provider lifecycle.

Architectural Wins

  • ✔ Interface shrinks: AuthProvider is relieved of database multiplexing.
  • ✔ Locality: Real-time configuration parameters sit close to queries.

🎯 Top Recommendation: Consolidate Offline Actions Sync Playback

We recommend tackling the Offline Actions Sync Playback candidate first. De-duplicating the Supabase database mutations between the Service Worker and the client-side main thread instantly simplifies the network layer. It restores single-point locality for database transactions, ensures 100% type-safety, and deletes over 150 lines of redundant, error-prone REST API call setups in the service worker.
