What is ClassHub — and what happens when you open it

From a Google tap to your personalized dashboard in under 3 seconds. Let's trace every invisible step.

A digital command centre for Section P2

ClassHub is a PWA built exclusively for SKIT Jaipur students. Every student in a section gets the same live feed — announcements, assignments, polls, schedules — locked so students from other sections can never see in.

Two types of users exist. Knowing the difference is essential when directing AI to build new features:

👤
Student

Views announcements, tracks attendance, submits assignments, votes in polls, calculates GPA. Read-mostly access — they consume information.

⚡
CR (Class Representative)

Posts announcements, creates polls, uploads assignments, tracks who submitted, manages subjects. Full write access — they produce information.

💡
Why this matters when you're steering AI

When you ask AI to "add a new feature," the user type determines which files change. A CR-only panel lives in different components than a student view — and different RLS policies control which database rows each role can touch.

Everything ClassHub can do

📢
Announcements

Section-wide messages with channels (Exams, Schedule, Campus), priority flags, and acknowledgment tracking so CRs can see who's actually read each post.

📝
Assignments & Submissions

CRs group tasks into assignment sets per subject. Students upload files (PDFs, code, images) directly inside the app — stored in Supabase Storage.

📊
Real-Time Polls

Live vote counts that update the instant someone clicks. General polls hide who voted using cryptographic hashing — more on this in Module 5.

📈
Attendance & GPA

Track attendance per subject with running calculations — how many classes you can still skip, how many you need to attend to reach 75%, and GPA target scenarios.

🔔
Push Notifications & Offline Mode

The app works even without internet. Actions taken offline (votes, acknowledgments) are queued and replayed automatically when you reconnect.

The @skit.ac.in rule — code and plain English, side by side

This exact snippet lives in src/components/AuthProvider.tsx. It runs immediately after Google confirms your identity — before a single piece of data loads.

TypeScript if (!user.email?.endsWith('@skit.ac.in')) { await supabase.auth.signOut() store.setAuthUser(null) store.setSession(null) navigateFn?.('/?error=domain') return }
Plain English
Check if the email ends in @skit.ac.in. The ?. safely skips the check if email is somehow missing.

Erase the user and session from the app's memory (the Zustand store).

🧠
A universal pattern: check early, fail loudly

Rejecting unauthorized users at the very first moment — before any data loads — is a cornerstone of secure app design. It's cheaper (less code executes), safer (nothing leaks), and easier to debug. You'll find this "guard clause" pattern in virtually every production app.

The golden rule for directing AI

03

Data Journeys — From Database to Your Screen

How do attendance percentages get from a PostgreSQL table in a Supabase data centre to a coloured bar on your phone? Let's trace every hop.

The problem every app has to solve

The database lives thousands of kilometres away on a Supabase server. Your phone screen updates in milliseconds. Bridging that gap involves three hard problems:

1
Loading states

The query takes 200–800ms. During that time the UI should show a skeleton, not a blank white screen or a crash.

2
Stale data

If you navigate away and come back, should the app re-fetch from scratch? That wastes bandwidth. But if it always shows cached data, you might see outdated information.

3
Synchronisation

If a CR posts a new announcement while you're on the Dashboard, your screen should update automatically — without you refreshing the page.

ClassHub solves all three with two tools working together: TanStack Query and Supabase Realtime.

TanStack Query: the app's personal librarian

Imagine a librarian who remembers every book you've ever borrowed. Ask for the same book twice in an hour and they hand it right back from memory — no trip to the shelves. But ask again tomorrow and they fetch a fresh copy, just in case it was updated. TanStack Query works exactly like that librarian.

📦
Cache

Every query result is stored in memory under a queryKey. Open the Attendance page twice in 5 minutes? Second visit is instant — served from cache.

⏱️
staleTime

After 5 minutes (configured per-hook), cached data is considered "stale." The next time you visit that page, a background refetch runs silently — you still see instant data, but it gets updated.

🔄
invalidateQueries

When the realtime event fires, ClassHub calls queryClient.invalidateQueries(). This immediately marks the cache as stale and triggers a silent background refetch — your screen updates without a page reload.

🔁
Mutations

When you submit data (vote in a poll, acknowledge an announcement), TanStack Query's useMutation hook handles the write, shows a loading state, and then refreshes the relevant cache on success.

The hook in code — useAttendance.ts

Here is the core of how ClassHub fetches attendance data. This lives in src/hooks/useAttendance.ts and is the exact code that runs in Step 3 of the animation above.

TypeScript — useAttendance.ts useQuery({ queryKey: ['attendance', userId], enabled: !!userId && isAuthenticated, staleTime: 1000 * 60 * 5, queryFn: async () => { const { data, error } = await supabase .from('attendance_records') .select(`present, absent, od, makeup, subjects:subject_id (code, name)`) .eq('user_id', userId) if (error) throw error return processAttendance(data) } })
Plain English
queryKey: The cache label. Results are stored under "attendance + this user's ID." Different users get separate cache entries.
enabled: Don't run the query until we have a userId AND the user is authenticated. Prevents spurious requests on page load.
staleTime: 5 minutes (1000ms × 60 × 5). Data younger than 5 minutes is served from cache without a network request.
queryFn: The actual database call. Fetches attendance records for this user, and also pulls in the subject name using a join (subjects:subject_id).
if (error) throw error: If Supabase returns an error (network failure, RLS rejection), throw it so TanStack Query can surface it as the error state.
processAttendance: Raw database rows become a clean JavaScript object — percentages calculated, "can skip" counts derived.
🧠
The join syntax: subjects:subject_id (code, name)

This is Supabase's PostgREST join syntax. It means: "also fetch the related row from the subjects table via the subject_id foreign key, and return only the code and name columns." One query, two tables — no second network request needed.

Always Live — Realtime, Offline Sync & the Service Worker

ClassHub stays in sync with the database 24/7. Here's the infrastructure behind that live connection — and what happens when it breaks.

The telegraph line that never closes

Normal web requests are like sending a letter: you send a question, wait, get a reply. WebSockets are different — they're a telephone line that stays open indefinitely. Once connected, Supabase can push a message to your browser the instant any database row changes.

ClassHub opens exactly one WebSocket channel per section when you sign in, managed by a file called realtimeBroker.ts. This is deliberate: one shared channel instead of one per page prevents duplicate connections and socket leaks.

announcements New post? UI updates instantly — no refresh.
assignments CR uploads a new set? Your Assignments page gets it immediately.
polls Someone votes? Live vote counts tick up in real time.
votes Each vote row triggers a realtime event.
submissions A student submits? The CR's command panel refreshes automatically.
acknowledgments Ack confirmed? The read-count badge updates for the CR.

One channel, many subscribers — reference counting

For Announcement Q&A (reactions and comments per post), ClassHub uses a pooled channel with reference counting. If three sibling components open the same announcement simultaneously, they share one WebSocket connection instead of opening three. When all three unmount, the connection closes. This prevents socket leaks.

What happens when you lose connection

ClassHub is a PWA — it's designed to keep working offline. Here's the four-step offline resilience system:

1
Detect disconnect

The browser fires an offline event. The app catches it, shows a toast ("Offline Mode"), and changes the sync status pill to orange.

2
Queue actions in IndexedDB

If you vote in a poll or acknowledge an announcement while offline, the action is saved to IndexedDB via offlineDb.ts. Nothing is lost.

3
Serve cached data instantly

The Service Worker (sw.js) has pre-cached the timetable and attendance data. You can still view your schedule and attendance figures — they load from the local cache.

4
Playback on reconnect

When connection returns, the browser fires an online event. playbackOfflineActionsClient() replays every queued action in order — polls, acknowledgments — against the live Supabase API. The sync pill turns green: "Synced."

The realtime channel — in code

This is the core of src/lib/realtimeBroker.ts. One function, one channel, six table subscriptions.

TypeScript — realtimeBroker.ts const channel = supabase .channel(`section-realtime-${sectionId}`) .on('postgres_changes', { event: '*', schema: 'public', table: 'announcements', filter: `section_id=eq.${sectionId}` }, payload => callbacks.onAnnouncement(payload)) // .on(...) repeated for polls, votes, assignments… .subscribe()   return () => supabase.removeChannel(channel)
Plain English
channel(...): Open a named WebSocket channel unique to this section. Two users in different sections get different channels — they never see each other's events.
.on('postgres_changes', ...): Listen for any database change (INSERT, UPDATE, DELETE) on the announcements table.
filter: section_id=eq.X: Only receive events for this section's rows — not every announcement in the entire database.
callbacks.onAnnouncement(payload): When an event arrives, call the callback function that was passed in — which triggers queryClient.invalidateQueries().
return () => removeChannel(channel): The cleanup function. When the user signs out, this closes the WebSocket so it doesn't keep running in the background.

Roles, Guards & the Poll Secret

Who can see what, who can do what — and why "anonymous" polls aren't actually anonymous to the database.

Three concentric rings of access

ClassHub has three nested access levels. Think of them as rings on a security badge — you need the outer ring to get in, the middle ring to access the app, and the inner ring to reach administrative tools.

🔑
Ring 1: Authentication

Must have a valid @skit.ac.in Google account and an active session. All other access checks come after this one passes.

🏛️
Ring 2: Section Membership

Must belong to a section hub. Without a section_id, you're routed to onboarding — you can't access any data pages.

⚡
Ring 3: Role (student vs CR)

CRs have write access — creating polls, posting announcements, managing assignments. Students have read access. The CR Command panel is invisible to students entirely.

🧠
An even rarer inner ring: isDeveloper

A handful of accounts have isDeveloper: true in their profile. These unlock the Developer Console and Subject Management pages — even if you're a CR, you can't access those without the developer flag. This is useful for app-level debugging without exposing it to all CRs.

Route guards — the bouncers at each door

In App.tsx, every route is wrapped in one or more guard components. These are React components that either render their children or redirect. They run before any page content loads.

RequireAuth No active session? Redirect to /. Blocks all app pages.
RequireHub No section_id? Redirect to /onboarding/choice. Blocks all data pages.
RequireDeveloper Not a developer? Redirect to /app/home. Blocks console and subject management.
RequireNoHub Already in a section? Redirect to /app/home. Prevents re-onboarding.
PublicRoute Already authenticated? Skip the login page and redirect to the app.
App.tsx — route definition <Route path="/app/home" element={ <RequireAuth> <RequireHub> <ErrorBoundary> <DashboardPage /> </ErrorBoundary> </RequireHub> </RequireAuth> } />
Plain English
To reach the Dashboard, you must pass through two bouncers in sequence.
RequireAuth checks first: do you have a valid @skit.ac.in session? No → login page.
RequireHub checks next: do you have a section_id? No → onboarding.
ErrorBoundary wraps the page in a crash net — if DashboardPage throws an error, it shows a friendly message instead of a blank screen.
Only if both guards pass does DashboardPage actually render.

Row-Level Security — the database's own bouncer

Route guards protect URLs in the browser. But what if someone bypasses the UI and calls the Supabase API directly with a valid session token? This is where Row-Level Security becomes the critical last line of defence.

🔒
Every table has RLS enabled

All 12 tables in ClassHub's schema have RLS turned on. By default, RLS blocks everything — no reads, no writes. Policies must explicitly grant access.

🏷️
Section scoping on every query

Every policy checks section_id = (SELECT section_id FROM users WHERE id = auth.uid()). Even if a student crafts a raw SQL query, they can only see rows from their own section.

✍️
Role-gated writes

INSERT and UPDATE policies on announcements, polls, and assignments check role = 'cr'. Students physically cannot insert announcement rows — the database rejects the attempt, no matter what the UI says.

⚠️
Why client-side role checks aren't enough

Hiding the "Post Announcement" button in the UI is nice for usability — but it's not security. A skilled person can open DevTools, call Supabase's REST API directly with their session token, and bypass every UI check. Only RLS, running inside PostgreSQL itself, is truly tamper-proof.

The anonymous poll trick — how ClassHub hides your vote without losing it

General polls display live vote counts but don't show who voted for what. Yet the database must prevent the same person voting twice. How do you prove uniqueness without storing the voter's identity?

ClassHub uses a hash function called calculate_anonymous_token, running in a secure Edge Function:

1
Token generation

When you vote, the app calls supabase.rpc('calculate_anonymous_token', { user_id, poll_id }). The Edge Function combines your user ID, the poll ID, and a secret server-side salt, hashes them together, and returns a token.

2
Vote stored with token, not user ID

The vote row is inserted with student_id: null and anonymous_token: <hash>. Your identity is never written to the votes table for general polls.

3
Duplicate prevention

The votes table has a unique constraint on anonymous_token. If you try to vote again, your token is the same (same inputs → same hash), and the database rejects the duplicate with a 23505 unique key violation.

The anonymous vote in code

This is the voting logic from src/hooks/usePolls.ts. Notice how the path forks based on whether the poll is anonymous.

TypeScript — useVotePoll mutation const isAnonymous = pollType === 'general' || pollType === 'anonymous' let token = null   if (isAnonymous) { const { data } = await supabase.rpc( 'calculate_anonymous_token', { user_id: userId, poll_id: pollId } ) token = data }   await supabase.from('votes').insert({ poll_id: pollId, option_id: optionId, student_id: isAnonymous ? null : userId, anonymous_token: token, })
Plain English
isAnonymous: True if the poll type is "general" or "anonymous." Named polls (like attendance check-ins) store the real student_id.
supabase.rpc(...): Call the calculate_anonymous_token Edge Function securely. It runs on Supabase's servers — the secret salt never reaches the browser.
token = data: The hash comes back as a string. It's deterministic — voting again produces the same token.
student_id: isAnonymous ? null : userId: Named polls store your real ID. Anonymous polls deliberately leave this null.
anonymous_token: token: The hash is stored instead. The unique constraint on this column prevents duplicate votes without needing the real user ID.
